# ADR-0136: The unmatched read-through — a settled box the corpus cannot name speaks its OCR text, under a per-session policy

Date: 2026-10-21
Status: accepted
Owners: agent worker (the live-box fix, the user's read-through request)
Related requirements/tests: docs/spec/05 (the commitment policy's abstention: "unclear whether text should be spoken → silence. Never invent dialogue to fill uncertainty"), docs/spec/14 (TTS text bounds and hostile-string handling for untrusted game content, trust zone C), docs/spec/13 ("did it speak, and why not" — the decision counters and the trace record), ADR-0092 (the fence and the one-terminal rule the read-through routes through), ADR-0115 (the glyph-noise trim the read-through reuses for its own evidence, §2), ADR-0137 (the placement-aware crop that makes the top-placed box readable at all — the read-through is its speech-side half), the live Wind Waker session 01M5E8CG (the session the user was playing: one empty `text.observed` in ~90 s, nothing ranked, committed or spoken)

## Context and constraints

The commitment policy is correct and deliberate: when the matcher abstains (the box's text is not in the corpus — an uncurated game, a new scene, a line the curator never imported), the session commits the box with `message_id "unknown"`, reason `COMMITTED_ABSTAINED`, `speech_eligible false`, and the speech layer stays silent (the policy's own words: never invent dialogue). On the board that is the right call for a *wobbly* read. The user's pushback is about the other case:

> "What if we should just read it, even if we don't have the dialogue correct… here it's not reading it at all, when the text is plain as day."

The two halves of that sentence are the requirement. The first names the policy: when the *text* is confident and stable — the box is already settled, which is exactly what a commit means (the commitment policy only commits a READY box) — the operator wants the screen's line spoken even though the corpus cannot name it. The second names the floor: a low-confidence read the matcher refused is not a line to improvise aloud, and the read-through must not become the matcher's back door.

Constraints: the Clef decision path for matched lines is untouched (a matched line the policy vetoed keeps its known message id and never reaches the read-through); the text is untrusted game content (docs/spec/14 trust zone C) and must be bounded and scrubbed before it reaches a TTS request; the board is CPU-bound (the read-through adds no recognition work — it runs on the commit event the session already emits); and the operator must be able to turn it off, per session, mid-run, with the switch visible on Play.

## Options

1. **Keep the spec silence (no change).** Rejected: it is what hurt the user. An uncurated game is the product's most common early state (the corpus is curated one game at a time), and in that state the narrator says nothing no matter how plain the line is on screen. The spec's "silence" clause is about *inventing* dialogue for an unclear read; a settled, confident read of what is actually on screen is not an invention.
2. **Always read through, no policy.** Rejected: it removes the operator's control over the behaviour the spec called silence, and it cannot be explained in the trace — a read-through and a matched narration would look the same in the event record.
3. **Read through, gated by a per-session setting (default ON), with the event naming why (chosen).** The gate is the commit's own verdict, not a re-derivation: `message_id "unknown"` **and** reason `COMMITTED_ABSTAINED` is the session's "no line matched, and nothing adjudicated into one" (the Clef path that resolved an abstain into a retrieved candidate returns a *known* message id and takes the matched route). The setting is a session property (the `session.settings_changed` channel, the partial-body contract of the settings route), ON by default — the user's words are the product's default — and the read-through's request carries `reason: "unmatched_read_through"` plus the OCR confidence, so the developer UI's trace answers "why did this line get audio" without a second system to consult.

## Decision

**The speech wiring reads through an abstained box when the session's policy says so.** The implementation lives in the runtime's speech layer (`internal/runtime/speech.go`), on the commit event the session already emits — no reducer change, no new pipeline work:

1. **The gate.** A commit with `message_id "unknown"` and reason `COMMITTED_ABSTAINED` (and `speech_eligible false` — the reducer's contract, unchanged) reaches the read-through when, and only when:
   - the session's `unmatched_read_through` setting is ON (the snapshot's documented default; the settings route moves it mid-session, the flag is read at the next commit — the catch-up switch's shape);
   - the commit's OCR confidence clears the floor (`0.75`, the tracker's mean read confidence — the tracker's own readiness floor of 0.55 raised, because this is a read with no corpus to vouch for it; measured against the live capture's clean top-box reads, where a full line reads at ~0.9+);
   - the occurrence is not already routed (the dedupe: the reducer commits one box occurrence once — region + lifetime + content — and the wiring's utterance table refuses to route an occurrence a second time, so the same box speaks at most once; a dismissed-and-re-shown box is a new lifetime and a new occurrence, the way a matched repeat re-speaks).
   A vetoed matched line (safe_to_speak, a non-narrated class) keeps its known message id and never reaches here: the Clef decision path is untouched for matched lines.
2. **The text.** The read-through speaks the **raw OCR read** (the commit's `raw_text` — case and punctuation as drawn; the commit's `text` field is the text machine's normalised comparison key, lower-cased), cleaned: line breaks joined into words, control characters dropped (the hostile-string half of docs/spec/14 — a `\u0007` is data the TTS request was never meant to carry), the box-edge glyph noise trimmed with the matcher's own trim (ADR-0115 §2 — the "4 ", "$o?" border reads), and the TTS text length bounded at 400 runes cut at a word boundary (docs/spec/14 "Bound … TTS text length"). A read that is all noise after the trim (no letter or digit) says nothing: the empty answer is the silent one, logged.
3. **The voice.** The speaker's voice when the commit carries a known attribution (`speaker_known` plus a `speaker_id` — the Clef decision's speaker answer), the profile's narrator fallback otherwise. The resolution runs on the line's *character*, not its message id: a read-through line has no message id in the corpus to look up, and resolving on the id would lose the attribution.
4. **The route.** The read-through line enters the audio pipeline through the same `routeUtterance` path a matched line uses — registration, the commit→voice sample, the catch-up decision, the fence move, the `speech.requested`, the worker, the catch-up batch — so it has one terminal, the fence supersedes its older generations (the box advanced), backpressure skips it with the matched line's reason, and the catch-up policy batches it. It prewarms nothing (its successors are not in the graph), and an ineligible commit's *matched* path still never fences — only a speakable line does.
5. **The event.** `speech.requested` for a read-through line carries, over the historic fields: `reason: "unmatched_read_through"` and `ocr_confidence` (the commit's confidence the gate read). The trace's join is the occurrence id: the commit (`message.committed`, `COMMITTED_ABSTAINED`, `speech_eligible false`) and the request together are the full answer to "why did this line get audio". A matched line's request carries exactly the historic fields (no reason), so the trace cannot confuse the two.
6. **The setting.** `unmatched_read_through` on the session: a plain bool, default ON, in the snapshot (`session.unmatched_read_through`) so the Play toggle reads the server's value, moved by `PUT /api/v1/sessions/{id}/settings` (the partial-body rule: a body that does not name it keeps the session's value). The switch decides what happens with lines committed *next*; a line already routed settles by its own terminal. The Play page's control bar shows the toggle (the same seam as the narrated-class toggles).

## Tradeoffs

- **The spec's "silence" clause becomes a default-ON policy.** The clause's intent — no invented dialogue for an unclear read — is preserved by the confidence floor and the gate's shape (a wobbly read the matcher refused stays silent); the case it did not intend to silence (a settled read of visible text) is now spoken, and can be re-silenced per session. The reversal is one flag default and a comment (below).
- **The raw read is the spoken text, not a curated one.** A read with an OCR error speaks the error (the TTS says "there" where the screen says "their"). That is the degradation the operator asked for — the line is spoken, the corpus is still curable afterwards — and the trace carries the confidence that lets the operator see which read-throughs were clean.
- **One more event shape on `speech.requested`.** Consumers that key the request's fields by the matched line's shape gain two optional fields; nothing the matched line carries changed.
- **The scenario harness's sidecar does not model the read-through.** The harness's own provider-layer speech sidecar gates on `speech_eligible` and keeps the historic silence for an abstained box (its catch-up machinery is the per-character-voices work's active surface, ADR-0132, and dragging the policy through there is not this change). The product path (the runtime's speech layer, the board, the developer UI) is the one that reads through; the harness records the commit's abstained verdict either way, so a scenario's "did it speak" expectation about *matched* lines is unaffected.

## Validation

- **Unit** (`internal/runtime/speech_unmatched_internal_test.go`): the cleaning path — line-break joins, control-character drops, the edge-noise trim, the all-noise silence, the word-boundary length bound and its no-boundary fallback; the word-char test.
- **Scenario** (`internal/runtime/speech_unmatched_test.go`, the manual-source deterministic suite, docs/spec/12):
  - `TestSpeechUnmatchedReadThroughSpeaksOCRText` — the matched line commits and speaks the Clef way (known id, no reason on the request), then the re-keyed second line commits as `unknown` / `COMMITTED_ABSTAINED` (the reducer's contract intact: `speech_eligible false`) and the read-through speaks the OCR text: the request names `unmatched_read_through` with the OCR confidence, the narrator's character (no attribution on the commit), the occurrence's identity and generation; the utterance starts and ends cleanly, the sink plays it, exactly one read-through request in the session (the dedupe), the snapshot carries the default ON.
  - `TestSpeechUnmatchedReadThroughOffStaysSilent` — the switch applied before the first frame (the manual source makes the order exact): the matched line still speaks (the Clef path untouched), the abstained box commits and stays silent — on the complete log, no speech event of any kind for the unmatched occurrence, no read-through reason anywhere.
  - `TestSessionSettingsReadThroughRoundTrip` — the settings surface: default ON in the snapshot, the switch off/on mid-session, the partial-body rule (a mode-only body keeps the value).
- **The captured-fixture replay** is ADR-0137's leg (the top-box frames read text now that the crop finds the band); the read-through's board proof is the live session that produced the complaint — the same frames that gave one empty `text.observed` now commit and speak.

## Consequences and reversal

- **Consequences.** A line without a corpus entry gets audio on the default policy; the trace distinguishes it by the reason; the operator's per-session switch and the confidence floor keep the spec's silence reachable; the matched path, the Clef path, the fence and the catch-up machinery are unchanged in shape (the read-through is one more caller of the shared route).
- **Reversal.** Set the default to OFF in `newSpeechWiring` and the `Start` snapshot (one flag), and the read-through becomes an opt-in; the gate, the event and the settings surface can stay — a session that wants it on keeps working. Removing the feature entirely is deleting `maybeUnmatchedReadThrough` and its helpers (the commit gate falls back to the historic `return`), the settings field (the partial-body contract ignores unknown fields), and the Play toggle — no schema, no migration, no cache-key change (the read-through's audio is synthesised under the occurrence's text, and no corpus text is invented).

## Amendment: plausibility gate (2026-10-21)

The original gate had a text-plausibility gap. The confidence floor gates the *read*; the trim and the 4-word-character floor gate the *length*; but the board proved the case the ADR did not name — a **settled, confident read of a screen with no dialogue box on it at all** (the live 2026-10-21 session: Link sailing, the text-presence check misfired, the crop reading the watermark, the frame border and the sprite corners). The ADR's "settled read of visible text" spoke that noise aloud: mark glyphs, currency and math symbols, one- or two-letter fragments and symbol-heavy runs (`™ a a`, `® ub, ok eww, nol.`, `> ™ ve ™ 1 mey.`, `wy, ¥`, `\ at 3`, `yyy`, …). Every one of them survived the trim (a word character remains) and most cleared the 4-word-character floor. The full evidence table — the exact strings the TTS request received — is the unit test's `boardSpokenJunk` list (below), not this body: the strings are the gate's regression fixtures.

**Decision.** A plausibility gate (`readthrough_gate.go`, `isReadThroughPlausible`) runs on the read-through's cleaned text where the noise trim is, and a rejected text gets exactly the empty-after-trim answer: silent, logged, no terminal (the line never routed into the pipeline, so there is no terminal to emit) — the log line is named `readthrough_implausible`, so the "did it speak, and why not" record names the rule. Every rule is one-sided in the direction the evidence demands: a rule that rejects junk may also reject a legitimate line (silence is this ADR's historic answer, and the per-session switch is still the operator's way back); there is no rule that trades silence for speaking junk. The rules, in rejection order:

1. **A non-dialogue symbol at a token start.** A dialogue token the screen drew opens with a letter (at best, the contraction's apostrophe); a token opening on an "other symbol" (the trademark, registered and copyright marks), a currency or a math symbol is the watermark, the border or the sprite edge, not the line.
2. **A run of one repeated letter** (case folded) of three or more: the watermark and border reads repeat a single glyph (the `yyy` shape), and no dialogue line does.
3. **The alphabetic share.** The letters as a share of the non-space characters, at least 0.70 — dialogue is letters with punctuation at the edges; the junk reads are symbols, marks and fragments (0.33–0.67). The floor sits just below the cleanest real line the gate must keep (an ellipsis line, 10 letters of 14 non-space characters, ≈ 0.714): the ellipsis is dialogue's own texture, so the floor clears it and the evidence shapes stay rejected.
4. **The alphabetic substance.** Two alphabetic word cores of at least 3 runes, or one of at least 5. A core is the token's inner run of word runes (letters and the apostrophes the contractions carry): the punctuation a line wears at its edges still counts its word ("wonder." is the 6-letter word the screen drew), and a mark glued into the middle of a fragment (`v™.`) counts for nothing.

**Tradeoffs.** A legitimate line that fails the gate stays silent: the ADR's historic answer for a read it cannot vouch for, with the operator's default-ON switch unchanged as the way back. The gate adds no recognition work — one string pass over text the session already committed — and no new event shape: the rejection is a log line, not an event, and a line that never routed carries no terminal, so the one-terminal rule (ADR-0092) is untouched. The share floor of 0.70 is the one deliberate tuning away from a rounder number: the ellipsis line is the tuning's floor case, and raising the floor to keep the junk out would make the gate eat dialogue the screen is plain about — the very failure the original ADR existed to fix.

**Validation.** Unit (`internal/runtime/readthrough_gate.go`, `readthrough_gate_test.go`): the evidence table — every string the board actually spoke is rejected and the short real lines the gate must keep ("Well, then?", "Hey! Over here!", "You found it!", "Hmm... I wonder.", "Thank you so much") pass — plus the rule-bucket tests that pin which rule owns which junk shape, so a later tuning cannot move a shape from one rule's coverage into a gap. Session: the read-through's existing scenario suite (`go test -race -run 'ReadThrough|Unmatched' ./internal/runtime/`) and the whole package (`systemd-run --user --scope -q -p MemoryMax=4G go test -race -timeout 20m ./internal/runtime/`) pass with the matched path's shape unchanged — the gate sits on the unmatched box's route only.

**Reversal.** Delete the gate's call from `maybeUnmatchedReadThrough` (the empty-after-trim answer becomes the whole text gate again) and `readthrough_gate.go` — no event, settings or schema surface is involved.
